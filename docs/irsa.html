Pods Without Passwords

How a container running in EKS reaches an AWS service with no access key stored anywhere — and why IRSA and OIDC are not two words for the same thing.

Written against cluster ai-interview-1 Region ap-south-1 For engineers new to AWS identity

The problem

Your pod needs a password it must never have

Our middleware pod has to read a database password out of AWS Secrets Manager. To call any AWS API you must prove who you are. So the pod needs AWS credentials.

The obvious answer is to create an IAM user, generate an access key, and hand it to the pod as an environment variable or a Kubernetes Secret. Almost every tutorial written before 2020 does this. It works. It is also the single most common way companies get breached.

Here is what you have actually done when you take that shortcut:

  • The key never expires. It is valid until a human remembers to rotate it. Most never get rotated.
  • It is copied everywhere. Your laptop, CI logs, a Slack message, a teammate's .env. Each copy is a new place it can leak from.
  • It is not attached to anything. A leaked key works from any machine on earth. AWS cannot tell your pod from an attacker in another country.
  • You cannot tell it was stolen. There is no signal. Someone else using your key looks exactly like you using your key.
The rule

A long-lived credential sitting in a file is a liability that grows every day it exists. The goal is not to store it more carefully. The goal is to never have one.

The answer

IRSA in one sentence

IRSA — IAM Roles for Service Accounts

Let a pod prove which Kubernetes ServiceAccount it is running as, and let AWS trade that proof for temporary credentials to an IAM role.

Nothing is stored. The pod holds a short-lived token that Kubernetes signs and rotates for it, and exchanges that token for AWS credentials that expire in about an hour. Steal the token and you have minutes, not forever. Steal the pod's disk and you find no secret at all, because there isn't one.

That is the entire idea. Everything below is the machinery that makes it true.

The question everyone asks

OIDC vs IRSA — what's the difference?

This trips up almost everyone, because the two words appear in the same sentences and the same setup guides. They are not alternatives, and they are not synonyms. They sit at different levels.

A standard — level 1

OIDC — OpenID Connect

An open industry protocol for proving identity with a signed token. Not AWS. Not Kubernetes. It is the same standard behind "Sign in with Google".

It defines how an issuer signs a token, how a token says who the holder is, and how anyone can fetch the issuer's public keys to verify a signature they did not create.

A specific use of it — level 2

IRSA — IAM Roles for Service Accounts

AWS's name for one particular application of OIDC: your EKS cluster acts as the issuer, and a pod's ServiceAccount is the identity in the token.

IRSA is OIDC plus EKS-specific plumbing — the projected token file, the eks.amazonaws.com/role-arn annotation, and the webhook that wires them together.

OIDC is the protocol. IRSA is a pattern built with it. Asking "should I use OIDC or IRSA?" is like asking "should I use HTTP or a REST API?" — one is made out of the other.

Proof: our AWS account has two OIDC providers

The clearest way to see the distinction is to look at what is actually registered in our account. There are two, and only one of them is IRSA:

Registered issuer Who presents the token Identity in the token Called IRSA?
oidc.eks.ap-south-1.amazonaws.com/id/FE398F… A pod in our EKS cluster system:serviceaccount:default:middleware Yes — this is IRSA
token.actions.githubusercontent.com A GitHub Actions workflow run repo:vikki-iam/react-app-k8s:ref:refs/heads/main No — just OIDC

Same protocol. Same AWS API call (sts:AssumeRoleWithWebIdentity). Same kind of trust policy. The only differences are who issues the token and what the identity string looks like.

When our GitHub Actions workflow assumes a role to deploy, that is OIDC federation — and nobody calls it IRSA, because there is no ServiceAccount and no EKS. When our middleware pod assumes a role to read Secrets Manager, that is the same mechanism, and AWS gave that specific arrangement the name IRSA.

Remember it this way

OIDC answers "how do you prove identity without a shared password?"
IRSA answers "how does a Kubernetes pod, specifically, do that on AWS?"

The mechanism

What actually happens when the pod starts

  1. The webhook spots the annotation
    Your pod uses ServiceAccount middleware. That ServiceAccount carries the annotation eks.amazonaws.com/role-arn. An admission webhook in EKS sees it as the pod is created.
  2. A token is mounted into the pod
    Kubernetes writes a signed JWT to a file inside the container and sets AWS_WEB_IDENTITY_TOKEN_FILE and AWS_ROLE_ARN. The token says "the holder is ServiceAccount middleware in namespace default", and Kubernetes rotates it automatically.
  3. The AWS SDK presents the token
    You write no code for this. boto3, the Java SDK and every other AWS SDK check those environment variables as part of their default credential chain, then call sts:AssumeRoleWithWebIdentity.
  4. STS verifies the signature, then the trust policy
    Two separate checks. First: is this token really signed by the issuer we registered? STS fetches your cluster's public keys to confirm. Second: does the identity inside the token match what this role's trust policy allows? Both must pass.
  5. Temporary credentials come back
    An access key, a secret, and a session token — valid for about an hour, scoped to exactly one IAM role. The SDK refreshes them before they expire, silently.
  6. The pod calls AWS
    GetSecretValue on the database secret succeeds, because the role's permission policy allows it. Anything the policy does not allow still fails — authentication and authorization stay separate.
The four pieces

What you actually create

For all that machinery, there are only four things a human sets up. The first is once per cluster. The other three are once per service.

PieceWhat it doesHow often
OIDC provider
in IAM		 Tells AWS "tokens signed by this cluster are worth listening to". Without it, STS has no reason to trust anything your cluster says. Once per cluster
IAM role The identity the pod becomes. Nothing special about it — an ordinary role. Once per service
Trust policy
on the role		 Who may assume this role. This is where the ServiceAccount name is pinned. The part that goes wrong. Once per service
Permission policy
on the role		 What the role may do once assumed. Ours allows reading two secrets, nothing else. Once per service
Trust vs permission

Freshers mix these up constantly. Trust policy = who can become this role. Permission policy = what the role can do. A role with a perfect permission policy and a wrong trust policy fails before it ever gets used — the pod cannot become the role at all.

Step 1 — register the cluster as an OIDC provider

Do this once. If you have already installed the AWS Load Balancer Controller on the cluster, it is already done — that controller uses IRSA too. 

# check whether it already exists
aws iam list-open-id-connect-providers

# create it if not (eksctl does the fiddly parts for you)
eksctl utils associate-iam-oidc-provider \
  --region ap-south-1 --cluster ai-interview-1 --approve

Step 2 — write the trust policy

This is the file that says which ServiceAccount may assume the role. Every value in it matters. 

{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Principal": {
      "Federated": "arn:aws:iam::043083733056:oidc-provider/$OIDC"
    },
    "Action": "sts:AssumeRoleWithWebIdentity",
    "Condition": {
      "StringEquals": {
        "$OIDC:sub": "system:serviceaccount:default:middleware",
        "$OIDC:aud": "sts.amazonaws.com"
      }
    }
  }]
}

The aud condition is not optional decoration. Without it the role is assumable more broadly than you intended. Always include it.

Step 3 — create the role and attach permissions

aws iam create-role --role-name ai-interview-dev-middleware \
  --assume-role-policy-document file://trust.json

aws iam put-role-policy --role-name ai-interview-dev-middleware \
  --policy-name read-secrets --policy-document file://read-secrets.json

Step 4 — annotate the ServiceAccount

This is the Kubernetes half. In our Helm chart it lives in templates/serviceaccount.yaml: 

apiVersion: v1
kind: ServiceAccount
metadata:
  name: middleware
  annotations:
    eks.amazonaws.com/role-arn: arn:aws:iam::043083733056:role/ai-interview-dev-middleware
Do not use eksctl create iamserviceaccount here

That command creates the role and a ServiceAccount. If your Helm chart already defines the ServiceAccount — ours does — you end up with two competing definitions and a confusing failure. Create the role only, and let Helm own the ServiceAccount.

The part that breaks

The sub string must match exactly

If IRSA fails, it is almost always this one line. The sub claim is a string Kubernetes builds from the pod's namespace and ServiceAccount name, and STS compares it character for character with what your trust policy says. There is no partial match and no helpful error.

system:serviceaccount:default:middleware
the namespace you deploy into — must equal the Helm --namespace flag the ServiceAccount name — must equal metadata.name in the chart

Three strings have to agree, and they live in three different files that nothing cross-checks for you:

WhereWhat it saysSet by
IAM trust policy system:serviceaccount:default:middleware you, in trust.json
Helm chart metadata.name: middleware templates/serviceaccount.yaml
Deploy workflow --namespace default NAMESPACE in the workflow env
A real mistake from this project

When we added our middleware repo to the GitHub Actions trust policy — the other OIDC provider — the string was written as …/ai-interview-middleware:refs/heads/main instead of …/ai-interview-middleware:ref:refs/heads/main.

One missing ref:. It looks almost right, and it never matches. Read these strings character by character — your eyes will fill in what you expect to see.

Debugging

What the errors actually mean

IRSA failures produce messages that point away from the real cause. This table is the translation.

Error in the pod logsWhat it usually meansFix
Unable to load credentials from any of the providers in the chain The pod got no token at all. The annotation is missing, or the pod is using a different ServiceAccount than you think. kubectl get sa middleware -o yaml and confirm the annotation is there
Not authorized to perform sts:AssumeRoleWithWebIdentity Token arrived, signature verified, but the sub did not match the trust policy. Namespace or ServiceAccount name is wrong. Compare all three strings in the table above, character by character
AccessDenied on GetSecretValue The opposite problem — the pod did become the role. Trust is fine; the permission policy is too narrow or names the wrong ARN. Check the resource ARNs in the permission policy, including the random suffix
InvalidIdentityToken The cluster's OIDC provider is not registered in IAM, so STS will not trust the signature. aws iam list-open-id-connect-providers
Pod is Running but never Ready Often not IRSA at all. The pod read its secret fine and is failing to reach the database. Read the actual pod logs before blaming IRSA

Prove it works, from inside the cluster

The fastest confirmation. If this prints the role ARN, IRSA is working end to end and any remaining problem is a permissions or application issue: 

kubectl run irsa-check --rm -it --restart=Never \
  -n default --overrides='{"spec":{"serviceAccountName":"middleware"}}' \
  --image=amazon/aws-cli -- sts get-caller-identity

The Arn in the output should read …:assumed-role/ai-interview-dev-middleware/…. If it shows the node's instance role instead, the pod fell back to the node — the annotation never took effect.

Recap

The five things to remember

  • No stored credential. That is the whole point. If your design still has a key in a file, you have not done IRSA.
  • OIDC is the protocol; IRSA is AWS's use of it for EKS pods. Our account proves it — two OIDC providers, only one is IRSA.
  • Trust policy is who; permission policy is what. They fail in different ways and the errors look nothing alike.
  • The sub string is the failure point. Namespace and ServiceAccount name, matched exactly, across three files.
  • Credentials expire in about an hour and refresh themselves. A stolen token is a short problem instead of a permanent one.
The mental model

Old way: give the pod a key and hope nobody copies it.
IRSA: give the pod a way to prove who it is, and let AWS decide, fresh, every hour.
